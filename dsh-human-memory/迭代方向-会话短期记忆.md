# 迭代方向：会话短期记忆（Session Short-term Memory）

> 记录一个**未来可能开发**的方向，当前版本（0.1.2）未实现。
> 目标：让 agent 在长会话里不必反复回看整段上下文，而是用「本会话的短期记忆」聚焦当前对话。

## 1. 问题

当前 DSH 每轮请求都会从会话日志派生完整历史。会话越长：

- 上下文越贵、越慢；
- agent 容易反复回看早期轮次、重复确认已做过的事；
- 真正与「当前这一步」相关的信息被淹没在长历史里。

## 2. 思路：给每个会话一份「任务状态」

为每个会话维护一份**会话短期记忆（session working memory）**，只存「当前任务的状态」，不存所有细节：

```jsonc
{
  "sessionId": "…",
  "goal": "把 dsh-human-memory 的设置卡片改成 settings.section",
  "done": ["读到 dsh-notify-say 的实现", "改完 client.js", "跑通 27 项自测"],
  "todo": ["验证卡片渲染", "更新文档"],
  "constraints": ["不改版本号", "删除不弹确认"],
  "lastUpdatedAt": 1793300000000
}
```

每轮结束更新一次（复用现有的 `agent/turn-stopping`），内容来自：

- 本轮用户意图；
- 本轮工具调用的结果（成功/失败/改了哪些文件）；
- 上一条短期记忆的状态。

## 3. 请求装配时只带「必要的」

理想的请求上下文：

1. 系统提示词；
2. **会话短期记忆摘要**（上面那份 JSON 渲染成短文本）；
3. 最近 N 轮原始对话（滚动窗口，N 可配）；
4. 按当前输入召回的相关长期记忆（`memory_recall`）。

更早的轮次不默认进入请求，但仍保留在会话日志里；需要时通过 `memory_timeline` 按需检索。

## 4. 与现有记忆层的关系

| 层 | 存什么 | 用途 |
|----|--------|------|
| 会话短期记忆（本方向） | 当前任务的 goal / done / todo / constraints | 决定「这一轮该关注什么」 |
| 工作记忆 `working` | 精确操作（文件、命令） | 细节，快速淡忘 |
| 情节记忆 `episodic` | 每轮「做了什么」 | 时间线检索 |
| 语义记忆 `semantic` | 长期事实/偏好 | 跨会话知识 |

会话短期记忆是**会话级**的，会话结束后可沉淀为情节记忆。

## 5. 可行性评估

**结论：可行，但属于中大改动，建议作为下一个大版本方向。**

有利条件：

- DSH 有 `agent/pre-step`（waterfall，可替换进入步骤的消息）与 `agent/request`（可替换请求配置）；
- 会话日志是唯一真源，被裁掉的轮次仍可通过 `memory_timeline` 找回；
- 已有 compaction seam（`compaction/*`）可参考。

需要解决的问题：

1. **工具调用链完整性**：不能把「tool/call 有、tool/result 无」的轮次裁掉；
2. **可恢复性**：被移出请求的内容必须仍能在日志里检索到；
3. **压缩质量**：短期记忆摘要需要 LLM 归纳，要防止丢关键约束；
4. **回归测试**：需要 A/B 对比「完整上下文 vs 短期记忆」的回答质量；
5. **不同模型窗口**：窗口大小差异大，需要按路由配置。

## 6. 分阶段计划（草案）

- **阶段 1（只读，不改请求）**：每轮生成会话短期记忆并展示，先观察质量。
- **阶段 2（可开关）**：`sessionMemory.enabled` 打开后，请求只带「摘要 + 最近 N 轮」，用 A/B 验证。
- **阶段 3（默认）**：质量稳定后再考虑默认开启，并提供「查看/编辑短期记忆」的设置界面。

## 7. 风险与边界

- 摘要错误会直接误导后续回答 → 必须保留原始日志可回查。
- 不能为了省 token 而丢掉安全/权限约束。
- 与「工作记忆」不要混淆：工作记忆是操作细节，短期记忆是任务状态。
- 暂不实现，先记录。
